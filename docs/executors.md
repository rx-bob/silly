# Bounded blocking executors

E6.S2 adds `run_runtime_with_executor(options, listener, wake, seed, io_worker, lane_worker)`.
The supervisor accepts connections only after every configured I/O worker and executor
lane reports successful startup. Listener and shutdown reader ownership follow `run_runtime`.
`run_runtime` itself rejects nonzero `options.executor.lanes`; it cannot silently launch
blocking work without the application's concrete executor bridge.

## Application wiring

Goose requires two concrete top-level thread entrypoints. Both receive copied flat seed
configuration. Each initializer creates its own app and any native resources in that owner.

```goose
thread_fn io_worker(start: silly::WorkerStart, seed: Seed) {
    silly::run_runtime_worker<Route>(start, seed, initialize, define, handle, lifecycle);
}
thread_fn lane_worker(start: silly::LaneStart, seed: Seed) {
    silly::run_executor_lane<Route>(start, seed, initialize, define, handle, lifecycle);
}
```

Register the execution class explicitly on each blocking route:

```goose
router.get("/report", Route.Report, silly::RouteOptions {
    execution: silly::ExecutionClass.Lane { index: 0 },
    ..
});
```

Route options default to `ExecutionClass.Inherit`: registration resolves the current scope
policy, which is initially `Inline`. An explicit `Inline` overrides an inherited lane. Configure `options.executor.lanes = 1` for
one serialized executor. A lane executes one task at a time. Counts 2–4 additionally
require `independent_lanes = true`: the application promises those independent owners
can safely run concurrently. There is no automatic cross-lane work stealing. Route
indices must exist in the configured lane set; invalid declarations fail startup.

Every I/O and lane owner builds a private immutable route plan. **Declare the same
ordered route inventory in every owner**: completion route IDs refer to that inventory.
Routes and app references never cross a thread boundary. Initialization receives
`Owner { id, lane }`; I/O owners use `lane = -1`, executor owners use their lane index.
Use that discriminator when constructing owner-specific resources.

The entire endpoint callback runs in the selected lane, including its `middleware`
call and endpoint cleanup. Inline routes continue on their I/O worker. The lane receives
owned copies of the admitted request head/body, selected policy and audit metadata.
Header/body/capture views are reconstructed locally and remain callback-scoped. No
`Context`, response builder, callback frame, borrowed app or native resource pointer is
sent through a queue. Lane handlers use the ordinary bounded buffered response APIs.
Streaming continuations remain E7 work. `run_executor_lane_with_errors` accepts a final
static error renderer callback and invokes it on the lane. Serialized lane error replies
are delivered without calling that renderer again on the I/O owner. Admission/deadline
failures generated by I/O use its own renderer, which must remain nonblocking.

## Capacity and deadlines

`ExecutorOptions` defaults to zero lanes, queue capacity 8 per lane and 8 outstanding
credits per I/O owner. Configurable input/output limits cannot exceed the fixed payload
capacities: 16 KiB head and 64 KiB body in either direction. `task_timeout_ms` defaults
to 30 seconds. Queue and credit capacities are validated positive and at most 1024.

Admission must obtain an owner credit and one queue slot without blocking. A refusal
returns a classified finite error response; it never waits for queue space on the I/O
thread. Default responses classify `QueueFull`/`Unavailable` as 503, `InputLimit` as
413, `OutputLimit` as 500, and `Deadline` as 504. Completion metadata retains the
`ExecutionOutcome`; a configured error renderer can customize the response.
The queue copies a complete flat `ExecWork` before its lane is notified. Replies
use distinct statically addressed `ExecReply<IoOwnerN>` queues. Each accepted task owns
one credit until its reply is consumed, including after client disconnect, timeout or
connection-slot reuse. That conservation reserves enough reply capacity even while the
I/O reader has stopped during shutdown. Full reply/report queues therefore represent a
protocol invariant violation, not a normal overload policy.

Reply application checks owner, slot, connection generation and request generation.
A late or stale reply releases its outstanding credit and cannot write into a reused
connection. An executing connection retains only its bounded existing input staging;
subsequent pipelined requests are dispatched sequentially after the response finishes.
Slow readers retain fixed output slabs, without an unbounded response queue.

Task deadlines include queue delay. Expired queued work is skipped. If a handler is
already running when its deadline or connection expires, the I/O owner can finish the
request's timeout/cancellation path while the task continues on its lane. Goose does
not forcibly interrupt a native call. Its later reply is discarded or classified late;
its credit is not prematurely returned. Aborts and nonreturning native calls are outside
the cooperative completion contract.

`RuntimeOptions.buffer_bytes_max` now reserves worker byte slabs plus fixed executor
payload storage. The conservative payload reservation is:

```
(lanes * (queue_max + 6) + workers * (outstanding_per_owner + 3)) * 81920
```

It is zero when no executors are configured. Fixed arrays reserve their full 81920-byte
head/body capacity even when configured admission limits are smaller. Additional terms
cover explicit lane/producer snapshots and response staging copies. As with the original
slab budget, connection/queue metadata, route storage, native thread stacks and compiler
scratch space are outside this counter. Queue capacities and route limits still bound
those logical owners; this is not a process-RSS promise.

## Lifecycle and shutdown

Each owner receives its own Start/Stop. The executor app receives HandlerFinished for
work that actually entered its endpoint. The I/O app receives TransferFinished when the
result is delivered or cancelled; it does not receive a duplicate HandlerFinished for
lane execution. Owned completion data carries handler outcome, entered middleware
layers, audit captures and the classified execution outcome across that boundary.
TransferFinished runs against the I/O app, not a borrowed executor app. If a task was
abandoned before its handler ran, no HandlerFinished is invented.

Initialization-created resources must be released by Stop, including failed startup.
Initializers and lifecycle callbacks must return cooperatively. Contained aborts cannot
recover arbitrary application handles; they poison the runtime and report the affected
owners explicitly.

Shutdown closes admission and sends lane stop requests immediately. Queued tasks are
abandoned; already admitted tasks may finish during the drain window. I/O owners deliver
ready responses until the deadline, then cancel remaining transfers. Lane Stop follows
its active task, while I/O Stop follows its own transfer cleanup; neither owner borrows
the other's app state.

Wake writers and task storage remain owned until every producer and monitor joins.
A noncooperative call yields `IncompleteDrain` and a resumable owned handle at the
deadline. Late replies after cancellation are discarded. The runtime lease is released
only after successful reclamation; aborted owners leave it poisoned. See
[shutdown and deadlines](shutdown.md) for the full contract.

## Named native-state registration

E6.S3 adds `ExecutorOptions.serialized_name`, a copied name bound exclusively to lane
zero. Names contain 1–64 ASCII letters, digits, underscores, hyphens or periods; an empty
option leaves numeric lanes unnamed. A named registration requires at least one executor.
Additional lanes still require the explicit independent-state promise. The name identifies
one process-wide owner under the existing runtime lease, not a separate lane per I/O worker.

```goose
let executors = silly::ExecutorOptions {
    serialized_name: "promptnook_native",
    lanes: 1,
    ..
};
router.scope("/api") {
    api =>
    api.execution(silly::Execution.Serialized { lane: "promptnook_native" });
    api.get("/database", Route.Database);
    api.get("/healthz", Route.Health, silly::RouteOptions {
        execution: silly::Execution.Inline,
        ..
    });
};
```

`Execution` aliases `ExecutionClass`. `router.execution(...)` changes the policy for
subsequent declarations in that scope; nested scopes inherit it and restore their parent's
policy on exit. Route options can explicitly override it. Startup rejects an unknown name
or missing executor registration. The entire selected endpoint—including middleware,
readiness checks, native operation sequences and cleanup—runs on that lane.

`owner.is_serialized("promptnook_native")` is true only for the named lane-zero owner;
it is false for I/O owners, unnamed lanes, other names and additional independent lanes.
Use this predicate in Start/Stop to keep native open/close on the owning lane. A pure
initializer may record the predicate, but must not initialize the same global native state
on every owner. Partial Start failures still get Stop; keep an attempted/initialized flag
and make application cleanup safe for the partial state.

The PromptNook reference uses concrete I/O and executor thread bridges, copied `AppSeed`,
and a named native scope. Its HandlerFinished hooks may touch native state only on the
lane. TransferFinished and I/O admission error formatting must not access that state.
See the [native inventory and migration boundary](promptnook_requirements.md#e6s3-native-ownership-boundary)
and [contract example](../examples/promptnook_contract/native_state.goose).

Goose thread-local app storage does not isolate C globals. This registration serializes
framework-dispatched native work; unrelated application threads must respect the same
boundary. Multicore native-handler execution requires separate handles, genuine native
thread-local state or process isolation. Socket workers remain independent while the
serialized native lane is busy.


The executable example is `examples/promptnook_contract/native_state.goose`.
`tests/runtime/native_state_test.goose` links only its small test-owned C adapter through a
per-test build sidecar; core `silly.build` still links only the transport shim.
The fixture detects wrong-thread access and interleaved DB/ZIP stages, gates each
sequence to overlap requests, verifies inline progress and an unrelated lane, and
checks native cleanup after active/queued shutdown and failed startup.
